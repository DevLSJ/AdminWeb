D'Guard KMS 구현 3주차 시연순서
주제: 사용자 관리 · 감사로그
기준일: 2026-09-02

== 1. 시연 전 안전 확인 ==

- 실제 고객 개인정보 대신 아래 예시용 가상 데이터만 사용한다.
  이름: 홍길동시연
  연락처: 010-9302-0001
  이메일: week3.demo.9302@example.com
- 원문 조회 사유에는 고객번호, 연락처, 이메일 등 개인정보를 적지 않는다.
- 감사로그는 append-only이므로 시연 후에도 삭제하지 않는다.

== 2. SQLTools 접속 및 1번 SQL 열기 ==

- SQLTools를 SSH 터널을 사용하는 `dguard_kms` PostgreSQL 연결로 접속한다.
- 로컬 파일: docs/week3_01_user_protection_verification.sql
- 원격 파일: sql/week3/week3_01_user_protection_verification.sql
- `--1.` 문장을 선택하고 Run Selected Querys로 DB, 계정, PostgreSQL 버전을 확인한다.
- `--2.`를 실행해 `app_user` 한 테이블에 암호문, IV, 마스킹, 검색 HMAC, 비밀번호 해시+Salt, 행 HMAC이 함께 있음을 보여준다.
- `--4.` 결과가 0행임을 보여 password/name/phone/email 평문 컬럼이 없음을 증명한다.

== 3. 사용자 등록 모달 시연 ==

- 웹에 ADMIN 또는 S.ADMIN으로 로그인한 뒤 `사용자 관리`(`/users`)로 이동한다.
- `사용자 등록` 모달을 열고 1번의 가상 데이터와 8자 이상의 시연용 비밀번호를 입력한다.
- 잘못된 이메일 또는 8자 미만 비밀번호로 유효성 검사를 먼저 보여준 뒤 정상 값으로 저장한다.
- 저장 직후 목록에 `홍****연`, `010-****-0001`, `we***@example.com`처럼 마스킹된 값만 나오는지 확인한다.

== 4. DB의 세 가지 보호 방식 시연 ==

- 1번 SQL의 `--3.`을 실행한다.
- IV가 필드별 12바이트이고, AES-GCM 암호문·PBKDF2 해시/Salt·검색 HMAC·행 HMAC이 모두 저장되어 있음을 확인한다.
- Salt는 비밀이 아니지만 패스프레이즈는 DB에 저장/백업하지 않음을 설명한다.

== 5. 마스킹 조회·정확 검색·페이징 시연 ==

- 이름 `홍길동시연`을 정확히 입력해 HMAC 정확 일치 검색 결과 1건을 확인한다.
- 연락처 `010-9302-0001`을 정확히 입력해 동일 사용자가 검색되는지 확인한다.
- 상태 ACTIVE/INACTIVE 필터와 페이지 크기 변경을 시연한다.
- 표와 상세에 이름·연락처·이메일 원문이 절대 나오지 않는지 확인한다.

== 6. ADMIN 원문 조회와 감사 기록 시연 ==

- 시연 사용자 행을 클릭해 상세 패널을 연다.
- `개인정보 원문 조회`를 누르고 사유를 `3주차 원문조회 감사 시연`으로 입력한다.
- 원문이 별도 경고 모달에서만 보이고, 닫은 후 일반 화면에 남지 않는지 확인한다.
- `감사 로그`(`/audit-logs`)에서 행위 `개인정보 원문 조회`를 검색한다.
- 행위자, 대상 UID, 입력한 사유만 남고 이름·연락처·이메일 원문이 없음을 확인한다.

== 7. 수정·상태 변경·비밀번호 재설정 시연 ==

- 상세의 `상세 수정`으로 연락처 또는 이메일을 바꾸어 저장한다. 기존 값을 채우는 원문 조회도 감사로그에 남는다.
- `사용자 정지`와 `사용자 활성화`를 순서대로 실행해 상태 변경과 감사 기록을 확인한다.
- `비밀번호 재설정`으로 새 8자 이상 비밀번호를 저장한다. 원문은 다시 보여주지 않고 새 Salt·PBKDF2 해시만 저장된다.
- 1번 SQL의 `--6.`을 실행해 `USER_UPDATE`, `USER_STATUS_CHANGE`, `USER_PASSWORD_RESET`을 확인한다.

== 8. 감사로그 검색·페이징·CSV 시연 ==

- 기간 from/to, 행위자, 행위 유형을 하나씩 적용하고 페이지 크기를 바꿔 서버 페이징을 확인한다.
- 임의의 감사 행을 클릭해 행 HMAC, 이전 연결, 다음 연결, 체인 헤드 결과가 모두 VALID인지 확인한다.
- `서명 CSV 내려받기`를 실행하고 파일 헤더에 prev_hash, row_hash, valid 값이 있는지 확인한다.
- 내려받기 자체가 `AUDIT_EXPORT` 감사 이벤트로 새로 남는지 확인한다.

== 9. 웹 해시 체인 기간 검증 시연 ==

- `기간 해시 체인 검증` 버튼을 누른다.
- 여정형 기간 선택 창에서 시작일시와 종료일시를 지정하고 `선택 기간 검증`을 누른다.
- 기간 내부 행 HMAC뿐 아니라 첫 행의 직전 연결, 마지막 행의 다음 연결 또는 최종 체인 헤드까지 검증함을 설명한다.
- 성공 알림에 선택 기간과 검사 건수가 표시되는지 확인한다.
- 검증 실패 시 실패 UUID 또는 기간 경계 이상을 경고한다는 화면 설명을 덧붙인다.

== 10. SQLTools 해시 체인·append-only 시연 ==

- 로컬 파일: docs/week3_02_audit_chain_verification.sql
- 원격 파일: sql/week3/week3_02_audit_chain_verification.sql
- `--1.`을 실행해 broken_links=0을 확인한다.
- `--2.`를 실행해 head_matches=true를 확인한다.
- `--3.`을 실행해 UPDATE/DELETE 차단 트리거를 확인한다.
- `--4.`를 실행해 SQLTools Messages에 `PASS: audit_log UPDATE blocked` NOTICE가 나오는지 확인한다. 예외은 블록 안에서 처리되며 실제 감사 행은 변경되지 않는다.
- `--6.`으로 `USER_VIEW_PLAIN`, `AUDIT_EXPORT` 이력을 확인한다.

== 11. 시연 마무리 ==

- 시연 사용자는 삭제하지 말고 INACTIVE 상태로 변경해 이력을 보존한다.
- 원문 모달과 내려받은 CSV를 닫고, 시연 중 화면 캡처에 개인정보 원문이 남지 않았는지 확인한다.
- 현재 적용 구조에서 패스프레이즈 교체는 전체 개인정보 재암호화 절차가 필요하므로 이번 시연에서 실행하지 않는다.
