과제 주제

아이넵의 통합키관리(D'GuardKMS)를 학습용으로 축소한 암호키 관리 어드민 웹을 본체로 구축하고, 여기에 어드민의 기본기인 사용자 관리와 게시판(공지사항 · 파일 업로드/다운로드)을 얹는다.

두 가지 키 — 역할이 다르다
  • 마스터키 · 어드민이 자기 DB에 저장하는 데이터를 보호하는 키. 사용자 개인정보와 게시판 첨부파일을 이 키로 암호화하고, KMS 관리 키를 저장할 때도 이 키로 래핑한다. 마스터 패스프레이즈에서 유도(PBKDF2)해 만든다
  • KMS 관리 키 · 외부 시스템이 연동해 쓰는 데이터 암호화용 키. 어드민의 역할은 이 키들의 생명주기 관리(등록·상태 전이·이력·사용 로그)와, 생성된 키가 제대로 동작하는지 확인하는 암복호화 테스트 기능 제공이다. 어드민 자체 데이터에는 사용하지 않는다
기술 스택 (권장 예시)
  • 백엔드 · Java 17, Spring Boot 3.x, Spring Data JPA, Spring Security(JWT), PostgreSQL 16, Gradle, springdoc-openapi
  • 암호 · PBKDF2-HMAC-SHA256(마스터키 유도 · 비밀번호 해시), AES-256-GCM(데이터 암호화 · 키 래핑), HMAC-SHA256(무결성 · 검색 해시), SecureRandom
  • 프론트엔드 · React 18, Vite, JavaScript, Ant Design, React Router, Axios, Recharts
  • 도구 · VS Code, pgAdmin 4, Postman, Git
스택은 예시이며 변경 가능하다
위 목록은 권장 예시다. 요구 기능과 암호화·무결성 요건을 충족한다면 언어·프레임워크·DBMS·라이브러리를 본인 판단으로 자유롭게 변경할 수 있다. 변경한 경우 08/17(월) 설계 발표에서 선택한 이유를 함께 설명한다.
최종 목표 상태
  • 기동 시 마스터 패스프레이즈로 마스터키를 유도하고 KCV로 검증한다
  • KMS 관리 키를 등록·조회하고 생명주기(상태)를 관리하며, 암복호화 테스트로 동작을 확인할 수 있다
  • 사용자 비밀번호는 단방향 해시 + Salt로, 연락처·이메일은 마스터키로 암호화
  • 게시판 첨부파일이 마스터키로 암호화되어 저장되고 복호화 다운로드된다
  • 키·사용자·감사로그 테이블은 무결성 컬럼으로 DB 직접 조작을 탐지한다
  • 모든 관리자 행위가 감사로그에 자동 기록되고 검색·내려받기가 된다
두 수행자는 동일 요구사항을 각자 독립 수행 (상호 협업·코드 공유 없음)
전체 키 구조 — 어느 키가 무엇을 보호하는가
마스터 패스프레이즈  ──PBKDF2-HMAC-SHA256(salt, 210,000회)──▶  마스터키 (AES-256)
   (환경변수)                                                      │
                                                                   ├──(직접 암호화)──▶ 사용자 개인정보  app_user.phone_enc · email_enc
                                                                   │
                                                                   ├──(직접 암호화)──▶ 게시판 첨부파일  암호문 파일 + notice_file.iv
                                                                   │
                                                                   └──(래핑/언래핑)──▶ KMS 관리 키  key_material.wrapped_key
                                                                                              │
                                                                                              ├─▶ 외부 시스템 연동 (과제 범위 외)
                                                                                              └─▶ 어드민 암복호화 테스트 기능 (과제 범위)

KMS 관리 키는 외부에 제공하기 위한 자산이므로 어드민 데이터를 암호화하지 않는다. 어드민이 그 키에 대해 하는 일은 생명주기 관리와 동작 검증(암복호화 테스트)이다. 반대로 어드민이 자기 DB에 저장하는 데이터는 전부 마스터키 하나로 보호한다.

KMS 관리 키의 생명주기 상태 전이 — 구현 2주차의 핵심 규칙
CREATED 생성→ ACTIVE 활성→ EXPIRED 만료→ INACTIVE 비활성→ DESTROYED 폐기
허용 전이 · CREATED→ACTIVE / ACTIVE→EXPIRED · INACTIVE / EXPIRED→INACTIVE · ACTIVE(재활성, 사유 필수) / INACTIVE→DESTROYED  ·  금지 전이 · DESTROYED에서 나가는 모든 전이, CREATED→DESTROYED 직행, 임의 역행  ·  암복호화 테스트는 ACTIVE 상태에서만 허용 (외부 연동 차단과 같은 의미)

테이블 구성은 예시이며 변경 가능하다
위 구성은 권장 예시다. 요구 기능과 암호화·무결성 요건을 충족한다면 테이블 분할·병합, 컬럼명·타입을 본인 판단으로 자유롭게 변경할 수 있다. 변경한 경우 08/17(월) 설계 발표에서 ERD와 함께 이유를 설명한다. 타입 표기는 PostgreSQL 기준이며, 다른 DBMS를 선택하면 동등한 타입(바이너리·JSON·타임존 포함 시각)으로 대체한다.

단, 다음 두 가지는 유지한다 — enc_ver는 어느 세대의 마스터키로 암호화했는지 표시하는 값(기본 1)으로 나중에 패스프레이즈를 바꿔야 할 때 구·신 데이터를 구분한다. audit_log는 append-only(UPDATE·DELETE 금지)다.

03마스터키 — 유도 · 보관 · 검증

어드민이 자기 DB에 저장하는 모든 데이터를 보호하는 단 하나의 키. 설계 단계에서 확정하고 구현 1주차에 만든다.

규격 및 유도 방식

항목값 / 방식
역할① 사용자 개인정보 암호화 ② 게시판 첨부파일 암호화 ③ KMS 관리 키 래핑
키 규격AES-256 (32바이트) · GCM 모드 사용
생성 방식비밀번호 유도 — 마스터 패스프레이즈에서 PBKDF2로 파생 (랜덤 키를 파일로 보관하지 않는다)
유도 함수PBKDF2-HMAC-SHA256, 반복 210,000회, 출력 32바이트
Salt16바이트 SecureRandom · 서버마다 다른 값 · crypto_config에 저장 (비밀 아님)
패스프레이즈 주입환경변수 KMS_MASTER_PASSPHRASE — systemd EnvironmentFile(권한 600, dguard 소유)
패스프레이즈 강도20자 이상 권장. 이 값의 강도가 곧 마스터키의 강도다
메모리 취급기동 시 1회 유도 → byte[]로만 보관 → 사용 후 Arrays.fill(key, (byte)0). String 사용 금지(GC까지 힙에 남아 힙덤프로 노출)
기동 시 검증KCV(Key Check Value) 대조 → 불일치 시 기동 실패(fail-fast)
분실 시복구 불가. 개발 환경에서 잊으면 DB 초기화 후 재시작
 
// 기동 시 1회
salt = crypto_config['salt']
masterKey = PBKDF2-HMAC-SHA256(env.KMS_MASTER_PASSPHRASE, salt, 210000, 32)

// KCV 검증
expected = crypto_config['kcv']
actual   = AES-256-GCM(masterKey, fixedIv, "KMS-KCV-V1")
if (!MessageDigest.isEqual(actual, expected)) throw → 애플리케이션 기동 중단

왜 KCV가 필수인가 — 이 방식의 최대 위험

비밀번호 유도 방식에서 패스프레이즈를 한 글자 잘못 입력하면 전혀 다른 마스터키가 만들어진다. 그런데 애플리케이션은 아무 오류 없이 기동한다.

  • 기존 데이터는 전부 복호화 실패한다 — 여기까지는 그나마 눈에 보인다
  • 새로 저장되는 데이터는 틀린 키로 암호화된다 — 이게 진짜 사고다. 나중에 올바른 패스프레이즈로 되돌려도 그 사이 저장된 데이터는 영구히 못 읽는다
  • KCV가 있으면 기동 자체가 실패하므로 잘못된 데이터가 한 건도 쌓이지 않는다
구현 규칙
KCV 검증은 애플리케이션 기동 시 수행하고, 실패하면 예외를 던져 기동을 중단한다. "경고 로그만 남기고 계속 진행"은 허용하지 않는다. KCV는 최초 마스터키 설정 시 생성해 crypto_config에 저장한다.

비밀번호 유도 방식의 구조적 제약

  • 패스프레이즈 변경 = 마스터키 변경 = 전체 재암호화 · 개인정보와 모든 첨부파일을 복호화 후 재암호화해야 한다. enc_ver 컬럼이 이때 구·신 데이터를 구분한다. 과제 범위에서는 구현하지 않고 제약으로만 문서화한다
  • 랜덤 32바이트 키보다 약하다 · 패스프레이즈가 약하면 오프라인 대입 공격에 노출된다. 반복 210,000회는 그 공격 비용을 올리는 장치다 — 반복 횟수를 낮추면 안 되는 이유를 설명할 수 있어야 한다
  • Salt는 비밀이 아니다 · DB에 두어도 된다. Salt의 목적은 비밀 유지가 아니라 같은 패스프레이즈에서 서버마다 다른 키가 나오게 하고 사전 계산(레인보우 테이블)을 막는 것이다
  • 백업 주의 · DB를 백업하면 salt·KCV는 함께 백업되지만 패스프레이즈는 백업되지 않는다. DB만 복원하고 패스프레이즈를 모르면 모든 암호화 데이터를 영구히 잃는다
실제 제품과의 차이 — 발표에서 설명할 항목
아이넵 D'GuardKMS는 이 역할을 물리 HSM(FIPS 140-2 Level 3)이 수행하며, 키가 HSM 밖으로 나오지 않고 스마트카드 + Passphrase 2단계 인증으로 접근을 통제한다. 이번 과제는 이를 환경변수 패스프레이즈 유도로 축소한 것이다. "우리 구현이 HSM 대비 무엇을 포기했는가"를 최종 발표에서 설명한다.
