# 운영 정책 관리 및 키 목록 표시

기준일: 2026-09-09. 기존 UI 구조·기본 정책(365일/30일)을 유지하며 심화 설정과 요청된 목록·달력 표시를 추가했다.

## 접근 및 적용 범위

- 메뉴: **운영 정책 관리** (`/settings`). S.ADMIN은 변경, ADMIN은 조회만 가능하다.
- 인증된 CLIENT도 등록/조회 화면에 필요한 설정 GET API를 사용할 수 있지만 설정 메뉴와 변경 권한은 없다.
- 알고리즘·용도·상태의 표시명, 설명, 정렬을 관리한다. 알고리즘·용도의 `enabled`는 신규 등록 허용 여부다. 편집 화면에서는 `신규 등록 허용`, `변경 사유`로 표시한다.
- 서버 지원 범위: AES-256-GCM + ENCRYPT/WRAP, RSA-2048-SHA256 + ENCRYPT. HMAC/SIGN/AUTH는 기존 데이터 조회 전용이다.
- 코드 추가·삭제와 상태 전이 수정 API는 제공하지 않는다. 상태 코드를 비활성화하거나 미지원 암호 기능을 활성화할 수 없다.
- 신규 생성·용도 변경은 서버에서도 검증한다. 기존 `DATA_ENCRYPTION` 요청 별칭은 ENCRYPT로 정규화한다. 이미 저장된 레거시 용도를 그대로 유지하는 메타데이터 수정은 가능하다.
- 알고리즘 신규 생성이 중지돼도 기존 키의 조회·암복호화·회전·폐기 기능은 유지한다.

## 날짜 정책

- 기본 유효기간: 초기 365일, 1~3650일. 새 키 요청에서 만료일을 생략하면 서버가 KST 오늘에 정책 일수를 더한다. 명시한 미래 만료일은 그대로 사용한다. 기존 키의 만료일은 소급 변경하지 않는다.
- 만료 알림일: 초기 30일, 1~365일. 웹 내부 경고 기준이며 이메일·문자 전송 기능은 아니다. 자동 회전 주기와 독립적이다.
- 대시보드 만료 목록·건수와 키 목록 기본 만료 조회는 KST 오늘부터 N일 후까지 양 끝 날짜를 포함한다. 기본 대상은 ACTIVE다. 키 목록에서 별도 상태/기간을 선택한 검색 기능은 유지하며, 기존 명시적 기간 조회 한도(3650일)도 유지한다.
- 저장된 날짜는 기존 UTC 자정 인코딩을 유지한다. 키 목록의 강조는 저장된 알림 정책에 해당하는 ACTIVE 키에 적용된다. 이미 만료된 키와 폐기·침해 상태는 만료 임박 강조에서 제외한다.
- 만료 임박 키의 전체 행은 연한 붉은색. 기존 무결성 오류의 더 진한 경고와 좌측 강조는 우선 유지한다.
- 상세 페이지에서는 같은 만료 임박 조건에 해당하는 키의 이름 옆에 시계 아이콘을 표시하며, 툴팁으로 만료일을 안내한다. 키 목록의 기존 강조 표시는 유지한다.
- 폐기는 공통 StatusBadge에서 회색 DeleteForever 아이콘으로 표시해 침해의 붉은 점과 구분한다.
- 등록 달력의 **보이는 월**과 **선택된 만료일**을 분리했다. 열 때마다 현재 시스템 월부터 보이며 365일 기본 만료일은 유지한다. 기존 30일/180일/1년 바로가기는 해당 날짜가 있는 월로 이동한다.

## 목록 번호

키·게시글·감사 목록은 DB 생성 순번을 `displayNumber`로 표시한다. 사용자 목록은 관리 계정과 서비스 사용자를 합쳐 생성 시각순으로 번호를 매긴다. 네 목록 모두 검색·정렬·페이지 이동으로 번호를 다시 매기지 않아 최신 항목의 번호가 가장 크다. 게시글 공지 우선 정렬은 유지한다. 키·게시글·감사 번호는 삭제·롤백에 따른 빈 번호가 있을 수 있으며 API 식별자는 계속 UUID를 사용한다. 사용자 번호는 현재 두 계정 테이블의 전체 생성 순위를 기준으로 계산한다.

## API와 동시 변경

| Method | Path | 권한 |
|---|---|---|
| GET | `/api/settings/key-codes` | 인증 사용자 |
| GET | `/api/settings/key-policy` | 인증 사용자 |
| PATCH | `/api/settings/key-codes/{group}/{code}` | S.ADMIN |
| PUT | `/api/settings/key-policy` | S.ADMIN |

변경 요청은 `version`과 2~200자 `reason`이 필수다. 버전 불일치 또는 동시 저장 충돌은 409를 반환한다. 화면은 사용자 편집 중 원본 버전을 보존하므로 새로고침 후 최신 값으로 다시 편집해야 한다.

변경 전후 값·행위자·사유는 `KEY_POLICY_UPDATE`, `COMMON_CODE_UPDATE` 감사 이벤트로 동일 트랜잭션에 기록된다. 공통코드 설명은 200자로 제한해 변경 전후 내용과 최대 길이 사유가 기존 감사 상세 1000자 안에 들어간다. 감사 필터의 ‘코드 · 정책’ 그룹에서 조회한다.

설정 조회는 로그인·브라우저 포커스 복귀·설정 화면 진입·키 등록 창 열기 시 갱신된다. 같은 화면에서 저장한 설정은 즉시 공유된다. 다른 관리자가 수정한 설정의 실시간 push는 제공하지 않으며 서버는 각 생성 요청에서 최신 정책을 검증한다.

## 마이그레이션·배포

V19는 `common_code`, `key_policy` 두 테이블과 기본 데이터만 추가한다. `crypto_config`, 기존 키, 만료일, 암호문·IV, 감사 행은 변경하지 않는다. Flyway를 끈 H2 개발/테스트 프로필은 초기화 컴포넌트가 같은 기본값을 생성한다. 운영에서는 Flyway가 초기 데이터를 생성한다.

프런트와 백엔드 변경이므로 두 서비스 배포가 필요하다. 기존 Dockerfile, Docker 컨텍스트 제외 규칙, Buildx 캐시, 서비스별 CI 선택과 배포 정책은 수정하지 않았다. 마이그레이션은 기존 대형 테이블을 갱신하지 않는다. 이전 앱 이미지로 롤백해도 신규 설정 테이블은 남으며 이전 앱은 이를 사용하지 않는다. 이전 프런트와 새 백엔드가 섞인 동안에는 예전 프런트의 365일/30일 명시값이 우선할 수 있으므로 신규 정책 변경은 두 서비스 배포 완료 후 수행한다.

## 검증 결과

- 전체 백엔드: **65/65 통과**, 실패·오류·스킵 0.
- 신규 정책 통합 테스트: **7/7 통과**. 권한, 날짜 기본값, 기존 데이터 보존, 기존 RSA 암복호화 유지, 버전 충돌, 코드 조합·일수 검증, KST 경계 확인.
- 임시 PostgreSQL 17 + Flyway V1~V19: 정책 7개 + 4주차 수용 22개, **29/29 통과**.
- 목록 번호 통합 테스트: H2 및 임시 PostgreSQL에서 각각 **4/4 통과**. 검색·정렬·페이징·공지 우선·삭제 후 번호와 감사 체인을 검증했다.
- 프런트 TypeScript/Vite 빌드 및 oxlint 통과.
- 실제 Chrome + React + Spring + PostgreSQL: **6개 시나리오 통과**, 페이지 예외 0. 행 배경·폐기 아이콘, 상세 만료 아이콘·툴팁과 비대상 숨김, 달력 재열기·시스템 다음 달, 정책 90일/7일 저장 후 등록·강조 반영, RSA 신규 생성 차단, 일반 ADMIN 조회 전용 화면 검증.
- 브라우저 기준 화면은 1440×1000. 테스트는 이 작업에서 생성한 임시 DB·샘플 계정만 사용했다. 운영 배포는 수행하지 않았다.

## 5분 시연 순서

1. 최고관리자로 설정 화면에서 초기 365일/30일과 코드 세 그룹을 확인한다.
2. 샘플 ACTIVE 키를 D+5, D+20, D+40으로 준비한다. D+5/D+20 행의 연한 붉은 배경을 확인한다. 침해·폐기 행의 서로 다른 표시를 비교한다.
3. 유효기간 90일·알림 7일을 사유와 함께 저장한다. D+20 강조가 사라지고 기존 키의 만료일은 유지됨을 확인한다.
4. 새 키 등록에서 달력은 현재 월, 선택된 기본 만료일은 오늘+90일임을 확인하고 실제 생성한다.
5. RSA 신규 생성을 중지한 뒤 등록 선택지와 직접 API의 차단을 확인한다. 기존 RSA 키의 조회·암복호화는 계속 가능하다.
6. 일반 ADMIN은 설정을 조회할 수 있지만 변경할 수 없음을 확인한다. 감사 로그에서 정책 변경과 체인 검증을 확인한다.

브라우저 자동 재현은 **샘플 전용 로컬 서버**에서만 실행한다. 스크립트는 테스트 정책을 초기화하고 샘플 키를 생성한다.

```bash
cd frontend
SETTINGS_E2E_URL=http://127.0.0.1:5189 \
SETTINGS_E2E_API=http://127.0.0.1:18089 \
SETTINGS_E2E_PASSWORD='<sample-account-password>' \
PLAYWRIGHT_MODULE='<installed-playwright-module-path>' \
node e2e/key-settings.cjs
```
